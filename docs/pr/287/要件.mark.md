# 要件

## 要望

`write_docs`・`delete_docs` と画面のサーバーからの直コミットの書き込み（`POST /sources/{source}/commits`）が、同じ配信元の書き込みのロックを待つ間に、文書の MCP の実行スロットを上限なしで持ち続けないようにする。

<!-- table: {"kind": "data"} -->

| 要件 | 終了の条件 |
| --- | --- |
| ロックの待ちと実行スロット | 同じ配信元のロックを持つ書き込みが続いている間に、同じ配信元へ実行スロットの本数（`DOCS_WORKERS`）を超える数の書き込みが来ても、ほかの配信元への `search_docs`・`write_docs` が実行スロットの待ちで時間切れにならない |
| 待ちの上限 | 同じ配信元のロックの待ちは、書き込みの期限（`write_deadline`）の内に収める。期限までに握れなければ、ファイルを書き換えずに `WriteDeadlineExceededError` を返却する |
| 既存の振る舞い | 同じ配信元の書き込みを 1 つずつにする排他と、ロックを握った後の書き込み・検査・直コミットの結果は変えない |

<!-- /table -->

`未確定`: ロックの待ち方（決める段: モジュール構成設計）

| 案 | 内容 |
| --- | --- |
| A | `SourceLocks.hold` に `RepositoryLocks.hold` と同じ待ち時間の上限（書き込みの期限までの残り）を持たせ、実行スロットの中で上限まで待つ |
| B | ロックの待ちを実行スロットの外（asyncio の側）で行い、握ってから実行スロットへ入れる |
| C | A と B の両方 |

推奨: A

`RepositoryLocks` と同じ待ち方に揃えられ、ロックを握る位置（`write_docs`・`delete_docs`・`_commit_locks` の中）を変えずに済む。待ちは書き込みの期限（32 秒）の内に収まるため、実行スロットを上限なしで持ち続けなくなる。
B はロックを握るまでに決まる値（書き込む先の解決・リポジトリの排他）と握る順序を asyncio の側へ移す必要があり、変更が `run_docs` の呼び出し方まで広がる。
