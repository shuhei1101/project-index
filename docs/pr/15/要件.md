# 要件

## 要望

dev-docs の develop（[adecc6c](https://github.com/shuhei1101/dev-docs/commit/adecc6c)）の文書の MCP・管理の MCP のうち配信元を扱うツール・配信元の読み込みと検査と変換・プラグインのフックとスキルを、設計書・テストと一緒に project-index へ移す。
dev-docs の画面のサーバーが使用する読み取り API と端末の設定の API を、特定の使い手に寄せない形で提供する。

| 要件 | 終わりの条件 |
| --- | --- |
| 文書の MCP の移行 | `describe`・`search_docs`・`trace_related`・`list_changes`・`list_match_words`・`write_docs`・`delete_docs` を、dev-docs を入れずに project-index だけを入れた端末から、今の dev-docs と同じ入出力で使用できる |
| 配信元の読み込み・検査・変換の移行 | 端末の設定に並べた配信元を読み込み、配信元のスキーマ・`validators[]`・`converters[]`・`generators[]` を今の dev-docs と同じく実行する |
| 管理の MCP の移行 | 配信元を扱う管理のツール（`check_project`・`reload`・`try_convert`・`write_nav`・`status` など）を project-index の管理の MCP から使用できる。移すツールはインターフェース定義設計で 1 件ずつ決める |
| プラグインの移行 | project-index のプラグインが、MCP の接続・SessionStart のフック（サーバーの起動と文脈の案内）・PreToolUse のフック（文書の MCP の入力への `cwd`・`session_id`・`agent_id` の上書き）・`global-setup`・`setup` のスキルを持つ |
| 配信元の設定のスキーマ・雛形・ツールの説明の移行 | `schemas/dev-docs.schema.json`・`templates/`・`content/prompts/` のうち索引の側が使用するものが project-index にあり、移した処理がそれを参照する |
| 配信元の設定の既定のファイル名 | 雛形・設計書・使い方の例と、名前で探す処理（dev-docs の `CONFIG_FILE`）の既定のファイル名が `project-index.yaml`・`project-index.local.yaml` になっている。端末の設定の `config` でほかの名前も指定できる |
| 読み取り API | Issue #14 の `### dev-docs の画面のサーバーが使用する入出力` の表の用途（配信元の一覧と状態・配信元の設定・文書の一覧・文書の取得・検討事項の文書・語での検索・リビジョンの一覧・端末の設定の配信元の取得と保存・端末の設定の配信元の 1 行の追加）を、表の入力で呼ぶと表の出力を返す |
| shuhei1101/dev-docs#119 の修正の移行 | 1 回の要求の中で ref の解決とスキーマの読み込みを繰り返さない処理と、その所要時間を確認するテストを移し、テストが pass する |
| 所要時間の測り直し | 移した後に、shuhei1101/dev-docs#119 の本文の表と同じ 3 つの要求（配信元 `ai-monitor` への name の絞り込み・`view: count`・body の正規表現）で所要時間を測り、索引のサーバーの計画書の `## テスト結果` に記録する |

影響するユースケースは、このリポジトリにまだシナリオが無いため、複合ユースケース設計・単一ユースケース設計でシナリオを作ってから表に加える。

`未確定`: 今の各リポジトリの `dev-docs.yaml` の移行方法（決める段: shuhei1101/dev-docs#163 のインターフェース定義設計。この作業 PR はその決定に合わせて名前で探す処理を作る）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 移行の間は `project-index.yaml` を先に探し、無ければ `dev-docs.yaml` を探す | 各リポジトリを一斉に改名しなくてよい | 2 つの名前を探す処理と、移行を終える時期の判断が残る |
| B | `project-index.yaml` だけを探し、反映作業で各リポジトリの `dev-docs.yaml` を改名する | 探す名前が 1 つで済む | 改名を各リポジトリへ一斉に反映する必要がある |

推奨: A

shuhei1101/dev-docs#163 の要件の推奨と同じ。配信は端末の設定の `config` で各リポジトリのファイルを直接指すため名前に依存せず、名前で探すのは管理の `write_nav`・`check_project` などに限られる。

`未確定`: 読み取り API の待ち受けを、文書の MCP・管理の MCP と同じプロセス・同じポートにするか（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 1 プロセス・1 ポート（`PROJECT_INDEX_PORT`）で `/mcp`・`/_admin/mcp`・読み取り API を待ち受ける | 今の dev-docs と同じ構成で、索引を 1 つのプロセスで共有できる | 読み取り API の応答の遅れが MCP の応答に響く |
| B | 読み取り API を別のポートで待ち受ける | 負荷を分けられる | 索引を 2 つのプロセスで持つか、プロセス間で共有する仕組みが要る |

推奨: A

アーキテクチャ図は索引のサーバー 1 つが MCP と REST を受ける構成で、dev-docs も 1 プロセス・1 ポートで稼働している。
