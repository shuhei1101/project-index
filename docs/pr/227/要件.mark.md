# 要件

## 要望

種類のスキーマが次の記載方法で定義した項目を、使える項目（`known_fields`）に含め、`search_docs` の `filter`・`order_by`・`group_by`・`fields` で指定できるようにする。
`known_fields` を呼ぶ `list_changes`・`write_docs` の `replace_text` の `filter`・`nav` の条件の確認も、同じ項目を受け付ける。

| スキーマの記載方法 | 満たすこと |
| --- | --- |
| `allOf`・`anyOf`・`oneOf`（最上位と、`properties`・`items` の中） | 各要素のスキーマの `properties` を、`allOf` などを持つスキーマと同じパスの項目としてたどる（最上位の `allOf` の `properties.top` は `top`、`a.allOf` の `properties.x` は `a.x`） |
| 循環して `$ref` のまま残った `#/$defs/...` | 参照先の定義の `properties`・`items` をたどる（`tree.children[].name`） |
| `$ref` を解決できず `$ref` のまま残った参照 | 今のとおり、たどらない |

- 型は今の決まりのとおり、同じパスで型が食い違うときは `string` にする（`anyOf: [{type: string}, {type: number}]` の項目も同じ）
- 今使用できる項目と型は変えない

循環する `$ref` をたどる深さは、インターフェース定義設計で A に決めた。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 同じ定義へ戻った時点で止める（`tree.children[].name` は項目にし、`tree.children[].children[].name` は項目にしない） | 項目の一覧が有限のまま作れる | 2 階層目より深いキーは指定できない |
| B | 同じ定義へ戻るパスを、どの深さでも項目として受け付ける（`children[]` の繰り返しをパターンで照合する） | どの深さのキーも指定できる | 使える項目の一覧（辞書）で表せず、条件の確認と近い項目の候補の出し方が変わる |

推奨: A

`known_fields` は項目のパスと型の辞書を返却し、条件の確認・近い項目の候補・`nav` の警告が同じ辞書を使用する。
B はこの辞書の構造を変え、呼び出し側を全て修正する。
今の要望の例（`uses[].id`・`category.id`）は 1 階層目で足りる。
