# 要件

## 要望

- setup のスキルが配信元へ書き出す管理用の YAML のスキーマが、knowledge の `schemas/knowledge-files.schema.yaml`（`design-schemas/v9.2.0`）と、ファイルの行のキー（`id`・`aliases`・`inject_when`・`category`・`related[].to`）とその説明で食い違わない
- project-index だけが使用する `checkpoint`（`project-index checkpoint` が記録し、`project-index changed` が参照する）は、配信元へ書き出すスキーマで引き続き検査できる
- 配信元へ書き出したスキーマは、配信元のフォルダの外のファイルを `$ref` で指さない（setup の後に `check_project` で違反が 0 件）
- 単体・結合テストのフィクスチャが参照する管理用の YAML のスキーマを、変更後のスキーマにそろえ、単体・結合テストが pass する
- フォルダ構成の設計書 [LAY-73-1](https://github.com/shuhei1101/project-index/blob/bd8a10107875ed36a301960c411c707043dc6cab/docs/layout/LAY-73-1.yaml) の `templates` の `files.schema.yaml` のエントリが、変更後のフォルダと一致する
- setup のスキル・シナリオ・インターフェース定義・モジュール構成・公開ドキュメントの `templates/files.schema.yaml` の記述が、変更後のスキーマの配置と一致する

`未確定`: 配信元へ書き出すスキーマの持ち方（決める段: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `templates/files.schema.yaml` を残し、ファイルの行のキーと説明を knowledge に合わせ、`checkpoint` を残す。`inject_when` は `$ref` を使用せず型を展開して持つ | knowledge を配信元に登録していない端末でも、setup がこれまでどおり 1 ファイルのコピーで済む | knowledge が変わるたびに手で合わせ直す |
| B | `templates/files.schema.yaml` を削除し、setup のスキルが `project-index.yaml` の `files` の行の `schema` に knowledge の参照（`source`・`path`・`ref`）を書き出す | 原本が knowledge の 1 か所になる | knowledge を配信元に登録していない端末では検査できない。`checkpoint` が knowledge のスキーマに無く、knowledge へのキーの追加が要る |

推奨: A

setup は knowledge を登録していない端末の任意のフォルダを配信元にするため、外部の配信元に依存しない 1 ファイルのスキーマのほうが setup の前提を変えずに済む。
