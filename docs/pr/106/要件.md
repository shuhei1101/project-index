# 要件

## 要望

setup の手順 4 で管理用の YAML の行へ仮のメタデータを付けるとき、次の段階で中身を参照する。

| 段階 | 参照するもの | 次の段階へ進む条件 |
| --- | --- | --- |
| 1 | 範囲の目次のページ（`index`・`README`・リンクを多く持つハブのページ）の全文。分類とタグの語彙を決め、ファイルを指すリンクの文字列と同じ行の説明を、そのファイルの `name`・`description` の材料にする。目次のページが無い範囲では飛ばし、タグは既存のタグだけから選ぶ | - |
| 2 | 取り出す手段が出すアウトライン（ファイルが既に持つ説明・見出し・サイズ・コードブロックの割合と言語・リンクの数・コードの関数名とクラス名と import） | 取り出す手段が、次へ進むと判定と理由を出したファイル（見出しが少ない・コードやログが大半・日本語以外） |
| 3 | 各見出しの直下の最初の段落 | `name`・`description` を決められない |
| 4 | コードブロックの外の文章 | `name`・`description` を決められない |
| 5 | 全文 | - |

- 機械的に取り出せる情報（アウトラインと段階 2 の判定）は、project-index が用意する手段の出力を使用し、エージェントは読み方を考えない
- タグは既存のタグ（`search_docs` の `group_by: tags`）と段階 1 で決めた語彙から選び、新しいタグは記載の前に示す表でまとめて示す
- 記載の前に示す表に、どの段階で決めたかを出す

2 回目以降の setup では、前回の確認の後に中身が変わったファイルだけを見つけ、メタデータを見直す。

- 変わっていないファイルは参照しない
- 見直したメタデータは上書きせず、今の値と新しい案を並べて示し、了承されたものだけ書き換える
- setup を終えるたびに確認の時点を記録する。Git 管理の配信元は HEAD の commit と、見直した未 commit のファイルの中身のハッシュ、Git 管理外の配信元は日時を記録する
- 変わったファイルは、次の表で見つける。記録したハッシュと今の中身が一致するファイルは除く（未 commit で見直したファイルを同じ中身で commit しても、もう一度見直さない）

| 管理用の YAML | 配信元のファイル | 記録がある | 記録が無い |
| --- | --- | --- | --- |
| Git 管理 | Git 管理 | 記録した commit から HEAD までの差分と、作業ツリーの未 commit の変更に出るファイル | 管理用の YAML を最後に変更した commit から HEAD までの差分と、作業ツリーの未 commit の変更に出るファイル |
| Git 管理外（ローカル運用） | Git 管理 | 同上 | 管理用の YAML の変更日時より後の commit の差分と、作業ツリーの未 commit の変更に出るファイル |
| Git 管理外 | Git 管理外 | 記録した日時より後に変更されたファイル | 管理用の YAML の変更日時より後に変更されたファイル |

`未確定`: 確認の時点の記録の置き場所（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 管理用の YAML の直下のキーに持つ | 配信元と一緒に commit され、別の端末・ワークツリーでも同じ起点になる | 管理用の YAML のスキーマ（`templates/files.schema.yaml`）にキーが増える |
| B | 端末の設定の `sources` の行に持つ | 管理用の YAML の形が変わらない | 端末・ワークツリーごとに起点がずれる |

推奨: A

ワークツリーごとに setup を回す運用で、起点が端末に閉じると同じ変更を何度も見直すことになる。
