### 管理用の YAML に無いファイルの判定（#133）

作業 PR [#131](https://github.com/shuhei1101/project-index/pull/131) で、ほかの有効な行の `paths` に該当するファイル（設計書の YAML・ほかの管理用の YAML 自身）は数えなくなった。
この作業 PR では、残りの次の 2 つを数えないようにする。

- より深いフォルダに配置したほかの管理用の YAML の範囲のファイル（`src/files.yaml` の行が本文に持つ `src/` の下のファイルなど）
- どの行の文書でもなく、利用者が管理用の YAML に記載しないと決めたフォルダのファイル（`docs/pr/` の下など）

setup の手順 4 の `project-index files` の結果（管理用の YAML の追加の候補）も、同じ判定で候補を出す。
`templates/project-index.yaml` の `files` の行は、判定の修正で直下のファイルを記載できるようになるかを確認し、要るときだけ修正する。

`未確定`: 「より深いフォルダの管理用の YAML の範囲」と、記載しないフォルダの指し方（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | ほかの `records: files` の行の管理用の YAML のフォルダの配下を、浅い管理用の YAML の候補から除外する。加えて、`documents[].exclude[]` に `/` を含む値を記載したときは配信元の `paths` の基準からのパスの glob として当て、フォルダごと除外できるようにする | 直下に `files.yaml` を配置するだけで、深い管理用の YAML の範囲を記載せずに済む。どの行の文書でもないフォルダも 1 行で除外できる | `exclude` の書き方が 2 通りになる |
| B | 判定は変えず、`exclude` に `/` を含む値の書き方だけを追加する | 判定の規則が増えない | 深い管理用の YAML を持つフォルダを全て `exclude` に記載する必要があり、フォルダを追加するたびに記載を追加する |

推奨: A

深い管理用の YAML のフォルダは、その管理用の YAML が記載を受け持つ範囲で、浅い管理用の YAML が重ねて数える理由が無いため。

### `worktree` を指定した読み取り（#134）

`worktree` を指定した読み取りと、作業場所がワークツリーの中にある読み取りで、そのワークツリーの配信元の設定（`project-index.yaml`）を再読み込みした配信元で文書を集める。
対象は `search_docs`・`trace_related`・`list_changes` で、`describe` は今の振る舞いを変えない。
`describe` がワークツリーの設定を再読み込みする処理は、読む場所を解く処理（`_target_of`）へまとめる（モジュール構成設計で確定）。

### setup の初回の索引の同期（#135）

setup の初回（`{config}` が無い場合）の後に、`check_project` の索引の同期の件数が 0 になる。
setup が手順 5 で作る `project-index.yaml` と、コピーする `schemas/*.yaml` を「管理用の YAML に無いファイル」に数えない。

`未確定`: 作ったファイルの扱い（決める段: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | setup の手順 5 で、作った `project-index.yaml`・コピーした `schemas/*.yaml` を、ほかのファイルと同じく仮のメタデータで管理用の YAML に記載する | 判定の規則が増えない。設定とスキーマも検索の対象になる | setup の手順が増える |
| B | 判定で、配信元の設定のファイルと `documents[].schema` が指すスキーマを候補から除外する | setup の手順は変わらない | 設定とスキーマを検索の対象にしたい配信元でも、記載が漏れても検出しない |

推奨: A

範囲の全てのファイルを管理用の YAML に記載する今の方針（`**/*` を既定の範囲にする）と統一され、記載の漏れを索引の同期で検出できるため。
