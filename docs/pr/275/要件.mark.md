# 要件

## 要望

- dev-docs の画面のサーバーが、書き込みの API（`POST /sources/{source}/commits`）で配信元の設定 `project-index.yaml` を直コミットで書き換えられるようにするかを決める
- 扱う場合、書き込む前に配信元の設定のスキーマ（`src/project_index/schemas/project-index.schema.yaml`）と配信元の設定の検証（起動・`reload` と同じ判定）に合格しない変更を断る
- 扱う場合、直コミットの許可は、端末の設定の `sources[].direct_commit.write_api_kinds` と配信元の設定の `direct_commit.kinds[]` の両方に許可が要る今の文書の考え方と同じにする
- 扱う場合、書き込みの API が書き換えた配信元の設定を、再起動せずに配信へ反映する

`未確定`: 配信元の設定を書き込みの API で扱うか（決める段: 単一ユースケース設計。規約『ユーザー確認が必須な事項』の「外へ出る・戻せない」「データの構造を決める」に当たるためユーザーへ確認する）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 扱う。`project-index.yaml` を直コミットできる対象にし、配信元の設定のスキーマと検証に合格した変更だけを書き込む | dev-docs#310 の画面から設定を修正できる | 誤った設定を既定のブランチへプッシュすると、その配信元が配信されなくなる |
| B | 扱わない。配信元の設定は Issue と PR を経て修正する | 配信を止める変更が PR のレビューを通らずに入らない | dev-docs#310 は配信元の設定の修正を画面から外す |

推奨: A

配信元の設定は既にスキーマと起動の検証を持ち、書き込む前に同じ判定にかければ配信を止める変更を断れる。許可も端末の設定と配信元の設定の両方に要るため、使わない配信元では今と変わらない。

`未確定`: 配信元の設定を指す方法（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 今の文書の種類 `root`（`files.yaml` の行の `body_file: path`）の本文として書き込み、本文を配信元の設定として検査する | 書き込みの API の要求の形が変わらない | `root` の種類の本文を書き換えられる配信元にしか使えない。種類の許可が `project-index.yaml` 以外の直下のファイルにも及ぶ |
| B | 書き込みの API に配信元の設定の項目（例: `sourceConfig`）を足し、文書とは別に許可（例: `write_api_config`）を持つ | 配信元の設定だけを許可でき、どの配信元でも同じに使える | 要求と端末の設定のキーが増える |

推奨: B

配信元の設定は全ての配信元にあり、文書の種類の定義に依らずに指せるほうが dev-docs#310 の画面が配信元ごとに分岐しない。
