# 要件

## 要望

- 配信元の設定の `documents[]` の行に、既定の検索から除く文書の条件を記載できる
  - 条件は `search_docs` の `filter` と同じ構造（条件・`and`・`or`・`not`）で記載し、共通のキー（`status` など）と種類の列を比べられる
  - 条件を記載しない行と、条件を記載しない配信元の結果は今と変わらない
  - 条件の構造の誤りは、配信元の設定のほかのキーの誤りと同じく起動・`reload`・`check_project` で違反として返却する
- `search_docs`・`list_changes`・`trace_related` の既定の結果から、条件に該当する文書を除く
  - `search_docs` の一覧・件数・集計（`group_by`）・取得のどれでも除く
  - `trace_related` は、除いた文書を関連の相手として返却しない
- 明示の引数を付けた呼び出しでは、除いた文書も検索・取得できる
  - 明示の引数を付けた結果では、除く条件に該当する文書をそれと分かるように返却する

`未確定`: `filter` の `id` の `eq` で文書を指した取得でも除くか（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `id` で指しても除き、明示の引数を付けたときだけ返却する | 除く規則に例外が無く、`filter` の条件の構造で結果が変わらない | 除いた文書の ID を知っていても、明示の引数を付けないと取得できない |
| B | `filter` が `id` の `eq` だけのときは除かずに返却する | ID を知っている文書はそのまま取得できる | `id` の条件を `and` で他の条件と組んだときの扱いなど、例外の規則が増える |

推奨: A

明示の引数を 1 つ付ければ取得でき、除く・除かないの規則が引数の 1 つだけで決定するため。

`未確定`: 除く条件のキーの名前と、既存の `documents[].search`（行全体を検索の対象から除外する真偽値）との関係（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 別のキー（例 `documents[].search_exclude`）を追加し、`search` はそのまま残す | 既存の `search` の意味と既定の結果が変わらない | 検索に関わるキーが 2 つになる |
| B | `search` を真偽値か条件を受けるキーに広げる | 検索に関わるキーが 1 つで済む | `search: false` の明示の引数での扱いなど、既存の値の意味を改めて決定する |

推奨: A

`search: false` は今は読み取り API の語での検索で行を除く値で、明示の引数で取得できる今回の条件とは振る舞いが違うため。
