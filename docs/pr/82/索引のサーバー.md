## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 書き込みの打ち切り | `write_docs`・`delete_docs` の処理に打ち切りの合図と期限を指定し、作業ツリーのファイルを置き換える直前に確認する。呼び出しが取り消された・期限を過ぎたときは書き込まずに時間切れのエラーを返却する。置き換えを始めた後は最後まで書き込む | 期限は非機能要件に追加する決定値 |
| 書き込まなかった理由の返却 | `_register` が `ProjectIndexError`・`ValidationError` 以外の例外（`GitError` など）を送出し直しているため、文書の MCP の全てのツールで、想定外の例外を例外の型と内容を持つ `isError` の応答に変換する。検査のスクリプトの制限時間超過は既に違反（`検査を実行できませんでした（…）`）として返却されるため、その振る舞いをシナリオとテストで固定する | 根拠は表の下 |
| ワークツリーを指定した読み取りの待ち | 所要時間の内訳をインターフェース定義・モジュール構成の工程で計測して原因を特定し、同じワークツリーの 2 回目以降の呼び出しで読み込みを繰り返さないようにする。上限を過ぎたら読み込み中である旨を返却する | 根拠は表の下 |
| 非機能要件 | 書き込みの期限と、ワークツリーを指定した読み取りの上限を、Claude Code の MCP のツールの呼び出しの時間切れから逆算して追加する | NFR-9 と同じ外部の制約 |

### 調査の結果

- サーバーのログ（`~/.local/state/project-index/logs/`、2026-11-14〜15）の `ツールの処理に失敗した` は全て `ProjectIndexError` でない例外だった。内訳は、スキーマの相対パスの `$ref` の解決の失敗（`ValueError: unknown url type: 'common.schema.yaml'`。違反の直し方を組み立てる `_schema_fix` で起きている。2026-11-15 のログには無い）と、`GitError`（`git archive` の 8 秒の待ち時間の上限、`git show` の `unable to read tree`）
- 検査のスクリプトの `ScriptError` は `DocumentChecker._run_validator` で違反に変換されており、`Error executing tool` の経路ではない
- 動いているサーバー（load average 24）へ、mdmark の既存のワークツリーを指定した `search_docs` を同じ接続から続けて送信した所要時間は、`view: ids` が 31.97 秒・46.13 秒、`summary` が 107.41 秒、`full` が 60.81 秒だった。2 回目以降も短くならず、呼び出しのたびにワークツリーを読み込んでいる。この PR の作業中にも、作ったワークツリーを指定した `search_docs` が `The operation timed out.` になった
