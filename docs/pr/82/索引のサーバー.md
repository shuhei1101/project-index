## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 書き込みの打ち切り | `write_docs`・`delete_docs` の処理に打ち切りの合図と期限を指定し、作業ツリーのファイルを置き換える直前に確認する。呼び出しが取り消された・期限を過ぎたときは書き込まずに時間切れのエラーを返却する。置き換えを始めた後は最後まで書き込む | 期限は非機能要件に追加する決定値 |
| 書き込まなかった理由の返却 | `_register` が `ProjectIndexError`・`ValidationError` 以外の例外（`GitError` など）を送出し直しているため、文書の MCP の全てのツールで、想定外の例外を例外の型と内容を持つ `isError` の応答に変換する。検査のスクリプトの制限時間超過は既に違反（`検査を実行できませんでした（…）`）として返却されるため、その振る舞いをシナリオとテストで固定する | 根拠は表の下 |
| ワークツリーを指定した読み取りの待ち | ワークツリーのファイルの一覧・本文のパスの解決・スキーマの参照の解決を、ワークツリーごとに保持し、同じワークツリーの 2 回目以降の呼び出しで繰り返さないようにする。保持した内容が古くなったかを確認する方法は、モジュール構成の工程で決める。上限を過ぎたら読み込み中である旨を返却する | 根拠は表の下 |
| 非機能要件 | 書き込みの期限と、ワークツリーを指定した読み取りの上限を、Claude Code の MCP のツールの呼び出しの時間切れから逆算して追加する | NFR-9 と同じ外部の制約 |

### 調査の結果

- サーバーのログ（`~/.local/state/project-index/logs/`、2026-11-14〜15）の `ツールの処理に失敗した` は全て `ProjectIndexError` でない例外だった。内訳は、スキーマの相対パスの `$ref` の解決の失敗（`ValueError: unknown url type: 'common.schema.yaml'`。違反の修正方法を組み立てる `_schema_fix` で発生している。2026-11-15 のログには無い）と、`GitError`（`git archive` の 8 秒の待ち時間の上限、`git show` の `unable to read tree`）
- `write_docs` の 4 件は全て `$ref` の解決の失敗だった。今のコードでは [abd0868](https://github.com/shuhei1101/project-index/commit/abd0868)（#42）の `check_schema` が `Unresolvable`（`_WrappedReferencingError` はその子クラス）を違反に変換する。`write_docs` がワークツリーの文書を置き換えるまでに通る git の呼び出し（`rev-parse HEAD`・`log`）はどちらも `GitError` を握りつぶし、`ls-tree` は `ref` を指したときだけ通る。今のコードには、`write_docs` で想定外の例外を毎回発生させる入力が無い
- 検査のスクリプトの `ScriptError` は `DocumentChecker._run_validator` で違反に変換されており、`Error executing tool` の経路ではない
- 動いているサーバー（load average 24）へ、mdmark の既存のワークツリーを指定した `search_docs` を、呼び出しごとに接続を張り直して続けて送信した所要時間は、`view: ids` が 31.97 秒・46.13 秒、`summary` が 107.41 秒、`full` が 60.81 秒だった。2 回目以降も短くならず、呼び出しのたびにワークツリーを読み込んでいる。この PR の作業中にも、作ったワークツリーを指定した `search_docs` が `The operation timed out.` になった
- Claude Code（2.1.325）の本体に同梱された MCP の SDK の `request` は、要求を中断したとき・時間切れにしたときに `notifications/cancelled`（`requestId`・`reason`）を送信する処理を持つ。`The operation timed out.` は同じ本体の中の中断の理由の文言。要求を記録するだけの HTTP の MCP サーバー（80 秒かかるツールを 1 つ持つ）へ、Claude Code 2.1.325 の `claude -p` から 2 回呼び出した（2026-11-15）。どちらも約 1 分で `The operation timed out.` になり、サーバーが受けた要求は `tools/call` の後に無く、`notifications/cancelled` は届かなかった。80 秒後にサーバーが応答を送信すると `ConnectionResetError` になった。Claude Code は時間切れのときに接続を切るだけで取り消しの通知を送信しないため、事象 1 を解消するのは書き込みの期限になる
- Claude Code の `.mcp.json` のサーバーの行は `timeout`（ミリ秒）を持てる。本体の説明は「サーバーごとのツールの呼び出しの待ち時間。`MCP_TOOL_TIMEOUT` より優先する。呼び出しごとの壁時計の上限で、進捗の通知では延びない」。プラグインの `.mcp.json`（`plugins/project-index/.mcp.json`）は `timeout` を持たず、この端末は `MCP_TOOL_TIMEOUT` も設定していない。HTTP の MCP サーバーへの要求 1 回の待ち時間は、本体の中で「サーバーの `timeout` か `MCP_TOOL_TIMEOUT`（60 秒未満は 60 秒に切り上げ、無ければ 60 秒）と `MCP_TIMEOUT`（既定 30 秒）の長い方」で決まり、既定は 60 秒。待ち時間を過ぎると `The operation timed out.` の `TimeoutError` で要求を中断する。呼び出しの壁時計の上限の既定（1e8 ミリ秒）と、応答も進捗も無いときの打ち切り（`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`、HTTP の既定 300 秒）は 60 秒より長い
- 端末の設定を knowledge と mdmark だけにしたプロセスの中で、mdmark の既存のワークツリーを指定した `search_docs` に cProfile をかけた（load average 17）。1 回目の `view: ids` は 41.23 秒で、そのうち本文のファイルの `realpath`（780 件）が 21.36 秒だった。2 回目の `ids` は 17.80 秒、3 回目の `summary` は 16.57 秒だった。2 回目の内訳は、`lstat` 5,211 回で 6.48 秒、スキーマの参照の再解決（`schema.py` の `resolve`）で 5.95 秒、`os.walk` 699 回で 5.11 秒、`stat` 820 回で 3.04 秒、glob の照合 185,696 回で 3.12 秒。`/mnt/c` の上で 1 回 1〜4 ms かかるファイルの問い合わせと、スキーマの参照の再解決を、呼び出しのたびに繰り返している

### モジュール構成で決めたこと

| 対象 | 決めたこと | 設計書 |
| --- | --- | --- |
| 期限と取り消しの合図 | 要求ごとに `CallLimits`（書き込みの期限・応答の上限・取り消しの合図）を作り、書き込み・削除・検査・mdmark の点検へ渡す。期限は `time.monotonic()` の秒で持つ | MOD-129（新規）・MOD-94・MOD-84・MOD-75・MOD-72 |
| 取り消し | `asyncio.CancelledError` を受けたら合図を立てて送り直す。スレッドの書き込みはファイルを置き換える前に合図を見て止まる | MOD-94・MOD-84 |
| 想定外の例外 | `_register` が `UnexpectedError: {型}: {内容}` の `isError` に変換し、トレースバックをログに残す | MOD-94・MOD-95 |
| ワークツリーの変更の確認 | たどったフォルダごとの更新日時を記録し、2 回目以降はフォルダの `stat` だけで確かめる。変わったフォルダがあればたどり直し、ファイルの中身の変更は今の `_files` の更新日時と大きさで読み直す | MOD-29・MOD-26 |
| 同じワークツリーの読み込みの重なり | 文書の MCP はワークツリーのパスごとに読み込みのタスクを 1 つだけ持ち、文書のストアはワークツリーごとの排他で 1 つずつ読み込む | MOD-94・MOD-29 |
| スキーマの参照の再解決 | 起動時のスキーマの `$ref` を解いた結果を (配信元, 行) でキャッシュする | MOD-29 |
| 端末の設定 | `write_deadline_sec`・`worktree_load_wait_sec` を追加する | MOD-67 |

`search_docs` に加え `write_docs`・`delete_docs` も、書き込む前に文書のストアの `load` でワークツリーの文書を全て読み込むため、同じワークツリーの読み込みの待ちを付ける。

フォルダの更新日時で変更を検出できるかを、`/mnt/c` の上の一時フォルダで測った（2026-11-15、WSL2・Windows 11）。

| 操作 | WSL 側 | Windows 側（PowerShell） |
| --- | --- | --- |
| ファイルの追加 | 変わる | 変わる（`New-Item`） |
| ファイルの改名 | 変わる | 変わる（`Rename-Item`） |
| ファイルの削除 | 変わる | 変わる（`Remove-Item`） |
| ファイルの中身の変更 | 変わらない | 変わらない（`Add-Content`） |
| `git checkout` で別のブランチへ切り替え | ファイルが増減したフォルダは変わる（WSL の git） | ファイルが増減したフォルダは変わる（git for Windows） |

中身の変更はフォルダの更新日時では検出できないが、`_files` のファイルごとの更新日時と大きさで検出する。追加・削除・改名はどちらの側からでも検出できるため、確認の方法は変えない。

配信元の行の読み込みの待ち（MOD-69 の `wait_for`）とスクリプトの実行（MOD-88）は変えない。
ワークツリーの読み込みの時間は、配信元の行の読み込みではなく、サービスの中の文書の集めで掛かっていたため。
