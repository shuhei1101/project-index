# 要件

## 要望

setup がプロンプトの `documents` の行（`content/prompts/**/*.yaml`、プラグインのルートは `{ルート}/content/prompts/**/*.yaml`）を記載するとき、その行の `paths` に当たるファイルを管理用の YAML（`files.yaml` / `files.local.yaml`）に記載せず、プロンプトの文書 1 件として配信する。

- 初回（`{config}` が無く、範囲を既定の `**/*` にした場合）: 管理用の YAML の追加の候補にプロンプトの YAML が出ない
- 2 回目以降（管理用の YAML に既にプロンプトの YAML の行がある場合）: プロンプトの行の候補と一緒に、その行の削除の候補が出る
- どちらも、記載した後の `check_project` が違反と索引の同期の件数を 0 で返し、`search_docs` がプロンプトの YAML 1 つにつき文書を 1 件だけ返す

`未確定`: 管理用の YAML のフォルダの配下にあるプロンプトの YAML を、索引の同期で「管理用の YAML に無いファイル」に数えない方法（決める段: インターフェース定義設計）

`documents[].exclude[]` はファイル名だけに当たり `/` を含めないため、`content/prompts/**` を管理用の YAML の行の `exclude` に書いて外すことはできない。
管理用の YAML のフォルダが配信元の直下（初回の既定）なら、プロンプトの YAML は管理用の YAML の配下になり、記載しないだけでは「管理用の YAML に無いファイル」に数えられる（[loader.py の unindexed_files](https://github.com/shuhei1101/project-index/blob/develop/src/project_index/features/documents/loader.py#L250-L281)）。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 索引の同期と `project-index files` が、ほかの `documents` の行の `paths` に当たるファイルを管理用の YAML の対象から外す。setup はプロンプトの行を記載するとき、その `paths` に当たる管理用の YAML の行を削除の候補にする | 設定.md の「他の行の `paths[]` に当たれば、その行の文書になる」と同じ考え方で、配信元の設定を書き足さずに済む | サーバーの索引の同期と CLI のコードを変える |
| B | `documents[].exclude[]` に `/` を含むパスの glob を書けるようにし、setup が管理用の YAML の行に `exclude: [content/prompts/**]` を記載する | 外していることが配信元の設定から読める | `exclude` の意味（ファイル名の glob）が変わり、スキーマ・検査・CLI の `--exclude` まで直す |
| C | setup が管理用の YAML を配信元の直下に置かない（プロンプトのフォルダを含まないフォルダに置く） | コードを変えない | 初回の既定の配置が変わり、範囲の既定の `**/*` と合わなくなる |

推奨: A

配信元の設定に書く値を増やさずに、同じファイルを 2 つの行で配信しない決まりをサーバー側で 1 か所に持てる。
