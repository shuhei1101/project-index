# 要件

## 要望

<!-- table: {"kind": "data"} -->

| No | 要件 | 終了の条件 |
| --- | --- | --- |
| 1 | 衝突しないときは今の直コミットのまま | 検査に合格しバージョンが合う要求は、今と同じ 1 回の要求でコミットするブランチへプッシュされ、ブランチもワークツリーも作成しない |
| 2 | 衝突したときだけ修正をブランチに残す | 検査には合格するがバージョンが合わない要求で、project-index がブランチを作成して要求の全ての書き込みと削除を 1 つのコミットにして残し、一時のワークツリーはコミットの後に削除する。応答はブランチの名前を返却する |
| 3 | ブランチの起点 | 画面が要求で送信した編集を始めたときのコミットからブランチを作成する |
| 4 | 検査に合格しない修正は今と同じに断る | スキーマ・validators・許可の検査に合格しない要求は、ブランチを作成せずに今と同じエラーで断る |
| 5 | 後の処理は端末のスクリプトに任せる | 端末の設定で指定したスクリプトを、ブランチを作成した後に project-index が実行し、スクリプトの結果を応答で返却する。スクリプトが失敗してもブランチは残る。指定が無ければブランチが残るだけ |
| 6 | スクリプトの指定は Git の管理外にだけ記載できる | スクリプトは端末の設定にだけ記載でき、配信元の設定（`project-index.yaml`）と、画面から書き換えられる端末の設定の API では指定できない |
| 7 | 項目ごとのバージョンを返却する | 読み取り API の文書の取得が項目のパスごとのバージョン（`value_hash`）を返却し、画面がそれを `expected_version` の辞書に指定して照合できる。同じ文書の別の項目の変更とは衝突しない |
| 8 | project-index は PR・GitHub の認証・AI Monitor の決まりを持たない | ブランチのプッシュ・PR の作成・ラベルは project-index のコードに入れない |

<!-- /table -->

`未確定`: ほかの変更が原因で断るとき（書き換える文書が削除された・ID が重複した 等）の扱い（決める工程: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | バージョンの不一致と同じくブランチに残す（起点のコミットで検査に合格すれば残す） | 利用者の修正が失われない | 解消する AI が削除・重複も扱う |
| B | 今と同じエラーで断る | 扱いが単純 | 利用者が手でもう一度修正する |

推奨: A

要望の「利用者の修正が失われない」に合うため。起点のコミットで検査に合格するかで残すかを決めれば、要件 4 と矛盾しない。

`未確定`: スクリプトの指定の配置先（決める工程: データ設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 端末の設定の最上位のキーにし、端末の設定の API の `sources[]` の外に配置する | 画面から書き換えられない | 配信元ごとに変えられない |
| B | `sources[].direct_commit` の中に配置し、端末の設定の API では受け付けない | 配信元ごとに変えられる | API が受け付けないキーの扱いが要る |

推奨: B

配信元ごとにプッシュ先や PR の作り方が違うため。端末の設定の API が受け付けないことで要件 6 を満たせる。
