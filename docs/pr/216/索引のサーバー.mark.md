## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 計測（稼働中のサーバー） | ロードアベレージ 8〜18 の間に 2 秒おきに 375 回、`/sources`（スレッドを使用しない）・`/sources/ai-monitor/config`（スレッドを使用する軽い処理）・`/sources/ai-monitor/docs/docs/data/DATA-3430-1.yaml` を取得した。文書の取得は 30 回が 1 秒を超え（最大 12.8 秒）、同じ時刻の `config` は最大 0.31 秒だった | スレッドの待ち（既定のスレッドプール）と配信元の読み込みの待ちは原因でない。文書の取得の処理そのものが延びている |
| 計測（commit が交互に届く） | `ref` に `c9cd618aa`（shuhei1101/ai-monitor#3693 のブランチ）を指した `docs/data/DATA-3694-1.yaml` と、`ref` を省いた `docs/data/DATA-3430-1.yaml` を交互に取得した。スレッド 0 本でも照合が 1.23〜1.34 秒（交互にしないときの約 20 倍）。稼働中のサーバーでは、ほかの commit の要求を挟んだ後の 1 回目が 8.8 秒、続けた取得が 0.5 秒前後 | dev-docs の画面（PR のブランチの `ref`）とエージェントの文書の MCP（`default_ref`）が同じ配信元を交互に読むため、commit の切り替わりのたびに照合し直す。応答は 33,837 バイトで、直列化は 1 ミリ秒に満たない。報告の約 744KB は project-index の応答では再現しない |
| 計測（同じプロセスの取り合い） | 同じプロセスに CPU を使用し続けるスレッドを 0・2・4・8 本立て、文書の取得の段ごとの中央値を測った。合計は 0.080・1.53・4.87・17.45 秒で、延びの大半は `DocumentStore.load` の照合（0.061 → 13.1 秒）と `read_target` の git の 2 回の呼び出し（0.012 → 1.12 秒） | 原因は GIL の取り合い。要求のスレッドは、要求の中で Python が進む量に比例して待つ。要求ごとに配信元の全てのファイル（ai-monitor は約 5,200 文書）を照合しているため、負荷の高い間に延びる |
| 性能 | 文書のストアは、Git のリビジョンの読み込みの結果を、配信元・commit・文書の行の定義の組ごとに持ち、同じ組の要求は照合せずに返す。文書のファイルのパス・本文のファイルのパスの索引も同じ組で持ち、文書の取得は索引で 1 件を引き当てる | 試作（スレッド 8 本）で 17.45 秒 → 0.33 秒。保持は配信元ごとに直近に使用した 5 つの commit までにして、超えたら最も古く使用した commit の結果から捨てる。5 は、読み取り API のログ（11 月 20 日）で 1 つの配信元に 10 分の間に届いた `ref` の種類の最大 3（`ref` を省いた要求を含む）に、文書の MCP の `default_ref` の 1 を加えた 4 に、安全率 20% を掛けて切り上げた値（規約『資源の値の決め方』の同時実行数）。ai-monitor の commit 1 つ分を追加で保持して増えるメモリは最大 72MB（tracemalloc の実測。読み込み直した文書を含む上限）で、5 つで最大 360MB |
| リビジョンの解決 | `resolve_ref` の commit の日時（`git show -s --format=%cI`）を commit ごとに保持し、要求ごとの git の呼び出しを 1 回（`rev-parse`）にする | commit の日時は変わらない |
| 既存機能への影響 | 応答の形・404・504 の振る舞いは変えない。文書の一覧・語での検索・文書の MCP の `ref` を指した読み込みも同じ読み込みの結果を使い回す | ワークツリーの読み込み（#197 の対象）は変えない |
