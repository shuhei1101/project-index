# 要件

## 要望

起動の直後、ほかの配信元の `default_ref` の commit の裏の書き出しが続いている間でも、利用者が開いた配信元の文書の一覧（`GET /sources/{source}/docs?values=true&common_keys=true`）が、書き出しが済んだ後の応答と同じ程度の時間で返る。

- 測り方: [Issue #145](https://github.com/shuhei1101/project-index/issues/145) と同じく、端末の設定の複製と空の状態フォルダで起動した直後に 14 件の配信元の文書の一覧を順に取得し、配信元ごとの 1 回目の応答時間を測る
- 基準: どの配信元の 1 回目も、dev-docs の画面の制限時間（45 秒）で打ち切られない。基準の秒数は PoC 検証で待ちの内訳を測った後に決め、非機能要件に置くかを設計で決める
- 裏の書き出しを残す目的（配信元ごとの最初の問い合わせを、要求の中の書き出しで時間切れにさせない。[#85](https://github.com/shuhei1101/project-index/issues/85)）は保つ

待ちの原因は、設計の前に PoC 検証で計測して確定する。
`SnapshotStore.checkout` の排他は commit ごとで、問い合わせが別の配信元の書き出しの終了を待つ経路は無い。
原因の候補は、裏の検査・裏の書き出し・要求の中の書き出しの CPU・I/O の競合（`tarfile` の展開は GIL を持つ）と、問い合わせた配信元の commit を裏の書き出しが書き出している最中の排他の待ち。

`未確定`: 直し方（決める段: PoC 検証）

| 案 | 内容 |
| --- | --- |
| A | 問い合わせを受けた配信元の書き出しを、裏の書き出しの順より先に進める |
| B | 問い合わせの応答の間は裏の書き出し・検査を止め、応答の後に再開する |
| C | 計測で見つかった競合の元（展開の方法・同時に動く処理の数）を減らす |

推奨: 計測の後に決める

案 A は「開いた配信元を先に読み込む」で、待ちの原因が書き出しの順でなければ解消しない。原因を確定してから選ぶ。
