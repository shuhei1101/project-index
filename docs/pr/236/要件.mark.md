# 要件

## 要望

常駐サーバーの稼働時間と呼び出すセッションの数によらず、文書の MCP と管理の MCP が上限の内に応答する。

| No | 要件 | 測る基準 |
| --- | --- | --- |
| 1 | 文書の MCP の全てのツールが、稼働時間によらず応答の上限の内に結果か「処理中」を返却する | 非機能要件『文書の MCP の応答の上限』（48 秒）を、起動から 6 時間以上・複数のセッションから呼び続けた後も超えない。同じ worktree の読み込みの所要時間が、起動の直後の計測（約 4 秒）から数倍の内に留まる |
| 2 | 管理の MCP（`status`・`restart` を含む）が、文書の MCP の処理が詰まっている間も応答する | 文書の MCP の要求と裏の処理が溜まった状態で `restart` を呼び、上限の内に応答して起動し直せる |
| 3 | 劣化の原因を特定する | Issue の候補（GIL の取り合い・捨てられた要求の蓄積・ヒープの増加と GC・`BackgroundGate` の優先度の逆転・管理の MCP の同居）と、設計書・コードから見つかる別の候補を、再現と計測で採否つきに切り分け、計画書の `## PoC 結果` に残す |
| 4 | 再発したときに原因を追える記録を残す | 稼働中のサーバーのログに、要求ごとの待ち（実行スロットの待ち・排他の待ち）と処理の時間、実行中・待ち中の処理の数、RSS を残し、ログだけで劣化の始まりと詰まった処理を指せる |

修正の方法と範囲: 切り分けで原因と分かった処理（呼び出しのたびにキャッシュ全体をたどる処理）を修正し、管理の MCP を文書の MCP の実行スロットから分ける。要件 1 の測る基準は本番と同じ負荷で実装後に測り、劣化が残れば該当箇所を修正して測り直す（[確認ログ](./確認ログ.yaml)）。
