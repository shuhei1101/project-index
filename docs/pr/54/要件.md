# 要件

## 要望

既存の応答のキーを残したまま、読み取り API の 2 つのエンドポイントへ、文書のストアが `resolve_metadata` で解決した `METADATA_KEYS` の全てのキーを返却する入出力を追加する。

| エンドポイント | 追加する出力 | 終わりの条件 |
| --- | --- | --- |
| GET `/sources/{source}/docs`（IF-24） | 各要素の、解決した共通のキー | 1 回の要求で、リビジョンの全ての文書の解決した共通のキー（`alias_type` は配信元の設定の行の値を含む）を受け取れる。クエリで求めたときだけ返却する構造にしてよい |
| GET `/sources/{source}/docs/{path}`（IF-25） | `metadata` の、解決した共通のキー | 文書の一覧と同じキーと値を、1 つの文書について受け取れる |

解決した共通のキーの値は、文書のストアが読み込んだときの `resolve_metadata` の結果をそのまま返却し、読み取り API の側で組み立て直さない。
キーの名前は `METADATA_KEYS` のまま（`main_tags`・`alias_type` などを camelCase にしない）にする。

`未確定`: 解決した共通のキーを配置する場所（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 各要素と文書の取得の `metadata` に、入れ子のオブジェクト 1 つを追加して共通のキーを入れる | `METADATA_KEYS` の `path`・`id` と、文書のファイルのパス `path`・文書の ID `id` が衝突しない。`METADATA_KEYS` が増えても応答の型を変えずに済む | 既存の `name`・`tags` などと値が二重に並ぶ |
| B | 各要素と文書の取得の `metadata` の同じ階層に共通のキーを並べ、衝突する `path` は別名にする | 階層が浅い | キーが増えるたびに応答の型を変える。別名の規則を dev-docs も持つ |

推奨: A

`METADATA_KEYS` だけが増えたときに、2 つのリポジトリで食い違わないことが要望の目的のため。

`未確定`: 文書の一覧で常に返却するか、クエリで求めたときだけ返却するか（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `values` と同じく、真偽のクエリで求めたときだけ返却し、それ以外は `null` にする | 求めない呼び出しの応答が増えない | 呼び出し側がクエリを指す |
| B | 常に返却する | クエリが増えない | `related` などで全ての呼び出しの応答が大きくなる |

推奨: A

Issue の本文がクエリで求めたときだけ返却する構造を認めており、`values` と同じ構造にそろうため。
文書の取得（IF-25）は 1 件だけを返却するので、常に返却する。
