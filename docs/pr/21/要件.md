### #6 配信元の設定の paths[] の基準のフォルダ

- 配信元の設定に、`paths[]` の基準のフォルダを指定するキーを追加する。基準のフォルダは、設定ファイルのフォルダか、それより上のフォルダを指定できる
- キーを省いた設定は、今と同じく設定ファイルのフォルダを基準に解く
- 基準のフォルダの外（`..`）を指す `paths[]` は、今と同じく違反にする
- 起動・読み直し・`check_project` で同じ解き方をする

`未確定`: 基準のフォルダを指定したとき、`paths[]` 以外の相対パス（`schema`・スクリプト・`scope.write` の既定）と「作業中の配信元」の判定を、どのフォルダで解くか（決める段: 単一ユースケース設計）

| 案 | 内容 |
| --- | --- |
| A | 配信元のフォルダそのものを基準のフォルダに置き換え、全ての相対パスと作業中の配信元の判定を基準のフォルダで解く |
| B | `paths[]`（と `exclude[]`）だけを基準のフォルダで解き、ほかの相対パスと作業中の配信元の判定は今どおり設定ファイルのフォルダで解く |

推奨: B

A は、基準のフォルダをリポジトリの直下にした配信元が、リポジトリの直下の配信元と同じ深さになり、作業中の配信元が決まらなくなる。`scope.write` の既定もリポジトリ全体に広がり、TH-407 の「設計書やコードまで参照できてしまう」懸念に戻る。

### #11 端末の設定の最上位の知らないキー

- 端末の設定の最上位に知らないキーがあっても、起動・読み直し・設定の画面の取得・保存・1 行の追加を続ける
- 保存では、知らないキーをファイルに残す
- 知らないキーは、キーのパスつきの警告として返す
- `sources[]` の行と `scope` の知らないキーは、今どおり違反にする

`未確定`: 警告を返す場所（決める段: インターフェース定義設計）

| 案 | 内容 |
| --- | --- |
| A | 起動・読み直しのログ、引数なしの `describe` の `warnings[]`、端末の設定の API の応答 |
| B | A に加えて、管理の MCP の `status`・`reload` の結果 |

推奨: A

Issue の一案と同じ範囲で、エージェントは `describe`、画面は端末の設定の API で気づける。`status`・`reload` は配信元ごとの状態を返す口で、端末の設定のキーの警告を足す理由が無い。
