| [#85](https://github.com/shuhei1101/project-index/issues/85) | 配信元ごとの最初の問い合わせ（`GET /sources/{配信元}/config`・`GET /sources/{配信元}/docs`）が、リビジョンの書き出しで数十秒かかり、`git archive` の 20 秒の上限を超えて 500 を返すことがある | 配信元ごとの最初の問い合わせも 2 回目以降と同じ程度の時間で応答する。上限を超えて止めたときは、止めた処理と理由が呼び出し元に伝わる |
| [#86](https://github.com/shuhei1101/project-index/issues/86) | 管理の MCP の `reload` が全ての配信元の検査を終えるまで応答せず、読み直しの完了を `status` で見分けられない | `reload` が一覧を差し替えた時点で応答する（または `status` で読み直しの最中・済んだことを見分けられる）。`docs/guide/管理のMCP.md` の `reload` の節に、応答の時点と済んだかの確かめ方がある。返却の `sources[]` の扱いを決め、意味を変えるなら破壊的変更を見直す |

「2 回目以降と同じ程度」は、[dev-docs#230](https://github.com/shuhei1101/dev-docs/pull/230) の計測と同じ条件（状態のフォルダを空にして起動し、14 件の配信元を 2 回ずつ開く）で、1 回目の応答時間が 2 回目の応答時間の範囲に収まり、500 を返さないことで確かめる。

`未確定`: `reload` の応答の時点（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 一覧を差し替えた時点で応答し、検査は裏で流す。`status` に読み直し・検査の最中であることを持たせる | 応答が数秒で返り、呼び出し元の時間切れが起きない | `reload` の返却の `sources[]` が検査の前の値になり、返却の意味が変わる |
| B | 今のまま検査を終えてから応答し、`status` に読み直しの最中であることだけを持たせる | 返却の意味は変わらない | 応答までの時間（14〜24 分）は変わらず、呼び出し元の時間切れは残る |

推奨: A

[#86](https://github.com/shuhei1101/project-index/issues/86) の事象は応答までの時間そのもので、B では呼び出し元が時間切れのたびにログで確かめる運用が残る。`sources[]` は `status` の `sources[]` と同じスキーマで、検査の結果（`sync`）は既に「検査が済んでいなければ `null`」を持てるため、A でも型は変わらない。
