# 要件

## 要望

`search_docs` で、種類のスキーマの配列の中のオブジェクトのキー（`uses: [{id: compare}]` の `id`）を項目として指定し、次を満たす。

| 引数 | 満たすこと |
| --- | --- |
| `filter` | 要素ごとの値と比べ、`op: eq` は完全一致で絞る（`compare` を指定して `compare-x` だけを持つ文書は該当しない）。要素のどれか 1 つが該当すれば文書が該当する（`match: all` は全ての要素） |
| `group_by` | 要素ごとの値で数え、1 つの文書に付いた同じ値は 1 件と数える（配列の項目の今の数え方と同じ） |
| `order_by`・`fields` | `filter`・`group_by` と同じ項目のパスを受け付ける |

受け付ける項目のパスの記載方法は、インターフェース定義設計で B に決めた。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `uses[].id` を受け付け、今は 0 件を返却する `uses.id` は配列の中のキーとして解釈して同じ値を返却する | どちらの記載方法でも該当する | 1 つの項目に 2 つの記載方法ができる |
| B | `uses[].id` だけを受け付け、`uses.id` は「知らない項目です」にして `uses[].id` を候補に出す | 文書のストアの項目のパス・`metadata` の列名（`tags[].name`）と記載方法がそろう | `uses.id` を指定していた呼び出しがエラーになる（今も 0 件で使用できていない） |

推奨: B

項目のパスの記載方法を文書のストアの `get_field` と `metadata` の列名の `[]` にそろえると、`describe(source, kind)` で参照したスキーマのキーと検索の項目が 1 つの記載方法で対応する。
`uses.id` は今も値が取れず、エラーと候補に変えても使用できていた呼び出しは無い。
