# 改名の参照元の書き換えと書き込みの後の通知の判定が文書の MCP の実行スロットを埋めないようにする

## 概要

エージェントが、ほかのエージェントの改名と書き込みの後の通知の判定が動いている間も、`write_docs` を時間切れにならずに実行できるようになる。

## 背景

[#281](https://github.com/shuhei1101/project-index/issues/281) の不具合。
2026-11-23 22:43 頃（JST）から文書の MCP の実行スロット 12 本が埋まったままになり、`write_docs` は処理が 0.1 秒でも開始まで 230 秒待って、呼び出し元が先に時間切れになった。
同じ日の 20 時台にも 28 分ぶん同じ飽和が記録され、21:47 頃に再起動したプロセスも約 55 分で再発した。
6 つのリポジトリのエージェントが設計書を書き込めず、[shuhei1101/ai-monitor#3781](https://github.com/shuhei1101/ai-monitor/issues/3781) などが作業を中断した。

飽和していたときのスタックでは、`write_docs` の改名の参照元の書き換え（`_rewrite_referrers`）が配信元の全ての文書のファイルを読み込み直して GIL を約 27 分持ち、同じ配信元の `write_docs` 3 本がその書き込みのロックを待ち、書き込みの後の通知の判定（`POST /_admin/post-write` の `classify_path`）7 本がワークツリーをたどる `os.walk` で止まっていた。
書き込みの後の通知の判定は、文書の MCP と同じ実行スロットで動き、エージェントがファイルを書き込むたびに呼ばれる。
