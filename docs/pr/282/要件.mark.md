# 要件

## 要望

改名の `write_docs` と、エージェントの書き込みのたびに呼ばれる書き込みの後の通知の判定（`POST /_admin/post-write`）が、文書の MCP の実行スロットを埋めないようにする。
ほかの配信元への `write_docs` と、改名と並行して呼ばれた `search_docs` などの文書の MCP のツールが、実行スロットの待ちで時間切れにならないことを終了の条件にする。

<!-- table: {"kind": "data"} -->

| 要件 | 終了の条件 |
| --- | --- |
| 改名の参照元の書き換え | 改名 1 件で、参照元の候補のファイルを 1 ファイルにつき 1 回だけ読み込む。`records` の行の文書も、同じファイルの行の数だけ読み込み直さない。改名前の ID・パスの文字列を本文に持たないファイルは YAML として読み込まない |
| 書き込みの後の通知の判定のたどり方 | `POST /_admin/post-write` の 1 回の要求で、配信元のワークツリーをたどる回数を、管理用の YAML の行の数に比例させない（1 回以下にする） |
| 書き込みの後の通知の判定の実行スロット | `POST /_admin/post-write` を文書の MCP の実行スロットで動かさない。判定が全て埋まっても、文書の MCP のツールの実行スロットの待ちが増えない |
| 実行中の要求の出力 | 管理の MCP の `status` で、実行スロットで動いている要求ごとのツール・配信元・経過秒を返却する。飽和したときに、改名を呼んだ要求と対象の配信元を権限なしで特定できる |
| 既存の振る舞い | 改名で書き換える参照元とその書き換えの結果、書き込みの後の通知の対象と文面は変えない |

<!-- /table -->

書き込みの後の通知の判定のたどり方は、1 回の要求でワークツリーを 1 回だけたどり、結果を全ての管理用の YAML の行で再利用する（モジュール構成設計で決定）。
管理用の YAML の行の `paths` は任意の glob を持てるため、ワークツリーをたどらずに管理用の YAML の場所を決める方法は、ファイル名が決まった行にしか使用できない。
たどった結果を `collect_files`・`unindexed_files` にそのまま指定でき、配信元の検査（載せるファイルの一覧）と同じ判定を保てる。
