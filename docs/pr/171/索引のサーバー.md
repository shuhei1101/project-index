結論: 不成立。
#160 の待ち（読み込みの完了待ち・要求の中の書き出し）の原因は、起動の直後に 10 本のスレッドで同時に読み込む配信元の行との GIL の取り合いで、要求の処理は経過が CPU の約 9 倍に延びる。
取り合いがあると、要求の中で何を処理しても同じだけ延びるため、書き出しを cat-file に替える・読む順番や数を変えるだけでは短くならない。
取り合いの除き方（行の読み込みを要求の応答中に休ませる箇所を `load_source` の中に配置する・行の読み込みを別のプロセスへ移す）は、この PoC で試していない。
#161 の 1 回目は YAML の読み込み（pure の ruamel.yaml）が約 9 割を占め、C 拡張は 3.5 倍速いが値の解釈が違い、そのままでは使用できない。

最小再現コードの要点（[#174](https://github.com/shuhei1101/project-index/pull/174) の diff）:

- `src/project_index/features/documents/store.py` の `_poc_load_catfile`・`_PocCatFile`: ls-tree の blob のパスを `walk_files` と同じ判定で絞り、`git cat-file --batch` を常駐させて blob の内容を `documents_from_text`（`read_body` に cat-file）へ指定する
- `src/project_index/features/sources/registry.py` の `_next_row`（構成 1a）と `LOAD_WORKERS`（構成 1b）、`row_load` の経過と CPU の記録
- `poc/run.sh`・`poc/analyze.py`・`poc/compare.py`・`poc/equal.py`: 起動 2 の条件（裏の検査と書き出しを止める）で 14 件を 2 回ずつ API で取得し、内訳と中央値、同じ commit での応答の一致を出す
