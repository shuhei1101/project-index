- 測り方: PoC PR [#153](https://github.com/shuhei1101/project-index/pull/153) の起動 2 と同じ条件（端末の設定の複製・空の状態フォルダで起動し、裏の検査との競合を除いた状態）で、読み取り API の文書の一覧（`GET /sources/{source}/docs?values=true&common_keys=true`）の応答時間と、その内訳（配信元の読み込みの完了待ち・要求の中のリビジョンの書き出し・`DocumentStore._load_table` の読み込み）を、#160 は配信元 dev-docs の 1 回目、#161 は配信元 ai-monitor の 1 回目と 2 回目で測る。測った時点の配信元の commit を計測ログに残す
- 画面での秒数は dev-docs の画面のサーバーの描画を含むため、判定は読み取り API の応答時間で行う
- 要求の中のリビジョンの書き出しを、起動の後の最初の問い合わせが前提にしない読み込み方にする（`## 変更箇所の由来` の判定）。裏の書き出しを残す目的（配信元ごとの最初の問い合わせを、要求の中の書き出しで時間切れにさせない。[#85](https://github.com/shuhei1101/project-index/issues/85)）は保つ

`未確定`: 応答時間の基準（決める段: PoC 検証）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | PoC 検証で #147 の後の develop の内訳を再計測し、内訳ごとに「今の値の半分以下」を基準にする | 計測した内訳に基づき、どの待ちを短くしたかを確認できる | 基準の秒数が PoC 検証まで決まらない |
| B | 今の値から固定の秒数にする（dev-docs の 1 回目 5 秒以下・ai-monitor の 1 回目 5 秒以下・2 回目 2 秒以下） | 着手の時点で基準が決まる | #147 の後の内訳を測らずに決めた値で、達成できるかが分からない |

推奨: A

#161 の 2 回目の 6〜9 秒は画面での計測で、API の応答時間と `_load_table` の時間を分けて測っていない（task-reviewer の受付時の任意の指摘）。測ってから基準を決定するほうが、達成できない基準での手戻りが無い。
