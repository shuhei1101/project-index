# 配信元を配信する

端末の設定と project-index.yaml を記載して project-index serve で配信し、文書の MCP で読む手順

## 手順

<!-- steps -->

1. 配信元のフォルダに `project-index.yaml` を置く。
   配信する文書の行を `documents[]` に記載する。
   ```yaml
   version: "3"
   name: knowledge
   description: どのプロジェクトでも使うコーディング規約
   documents:
     - id: rules
       paths: [docs/rule/*.yaml]
       title: 規約
       schema: schemas/rule.schema.yaml
   ```
2. 端末の設定 `${XDG_CONFIG_HOME:-~/.config}/project-index/settings.yaml` に配信元の行を追加する。
   別の場所に置くときは、環境変数 `PROJECT_INDEX_CONFIG` でパスを渡す。
   ```yaml
   version: "1"
   clone: /home/me/repo/project-index
   sources:
     - id: knowledge
       config: /home/me/repo/knowledge/project-index.yaml
       scope:
         read: [/home/me/repo/ai-monitor/**]
         write: [/home/me/repo/knowledge]
   ```
3. サーバーを起動する。
   ```bash
   project-index serve
   ```
4. 標準出力に出た、配信している配信元の ID を確かめる。
5. Claude Code から `http://127.0.0.1:8786/mcp` に接続し、文書の MCP で読み書きする。

<!-- /steps -->

## Git のリポジトリを配信する

Git のリポジトリの配信元は、端末の設定の `sources[].config` にメインのリポジトリ（クローン本体）の `project-index.yaml` を指します。
ワークツリーの `project-index.yaml` は指しません。

| 読むもの | 読む場所 |
| --- | --- |
| 文書（`ref` を省いたとき） | `project-index.yaml` の `default_ref`（既定 `develop`）のリビジョン |
| `project-index.yaml`・`documents[].schema` のスキーマ・`validators`・`converters` のスクリプト | `default_ref` のリビジョン。クローン本体が別のブランチを checkout していても `default_ref` から読む |
| 作業中の文書・設定・スクリプトと、`generators` のスクリプト | `cwd` か `worktree` の引数が指すワークツリー |

`default_ref` は、ディスクにある先頭の `project-index.yaml` の値を使います。
サーバーは要求のたびに `default_ref` の commit を確かめ、進んでいれば配信元を組み立て直します。
`default_ref` へマージした設定は `reload` なしで配信に入ります。

その端末だけの設定（`project-index.local.yaml` など）は、`.gitignore` して先頭に置けます。
先頭の設定の配置先で、読む場所が決まります。

| 先頭の設定 | 読む場所 |
| --- | --- |
| `default_ref` にある | 設定・スキーマ・スクリプトを `default_ref` から読む |
| `default_ref` に無く、`.gitignore` で無視されている | 先頭の設定だけをディスクから読む。スキーマ・`validators`・`converters` のスクリプトは `default_ref` から読む |
| `default_ref` に無く、`.gitignore` で無視されていない | 「`{default_ref} に {パス} がありません`」でその配信元を配信しない |
| Git の外のフォルダ | 設定・スキーマ・スクリプトを全てディスクから読む |

作業はワークツリー（既定 `.claude/worktrees/*`）で行い、文書の MCP の読み書きもワークツリーに向けます。
`worktrees[]` の相対パスはメインのリポジトリの直下から数えます。
配信元のブランチ・タグと、`worktrees[]` に当たるワークツリーのパスと checkout しているブランチは、`describe(source)` で引けます。

## コミットできないリポジトリを配信する

`project-index.yaml`・管理用の YAML・スキーマをコミットできないリポジトリは、project-index のために追加するファイルを全て `*.local.*` の名前で置き、Git に無視させるローカル運用で配信します。
端末の設定の行の `storage.type` を `disk` にすると、Git を参照せず、登録したフォルダのファイルで索引と検索を行います。

| ファイル | コミットする運用 | ローカル運用 |
| --- | --- | --- |
| 配信元の設定 | `project-index.yaml` | `project-index.local.yaml` |
| 管理用の YAML | `files.yaml` | `files.local.yaml` |
| スキーマ | `schemas/files.schema.yaml` など | `schemas/files.schema.local.yaml` など |
| `validators`・`converters` のスクリプト | 任意の名前 | `*.local.*` の名前（例 `scripts/check.local.py`） |
| Git が無視する設定 | 無し | `git rev-parse --git-path info/exclude` の指すファイルに `*.local.*` の 1 行 |

- `.gitignore` はコミットするファイルなので書き換えない
- `*.local.*` は、リポジトリの中の Git が追跡していない同じ名前の構造のファイル（`settings.local.json` など）も無視する
- `*.local.*` の名前のファイルは、管理用の YAML に記載しない（コミットする運用の配信元でも、索引に無いファイルに数えない）
- クローン本体で `develop` などを checkout して作業し、ワークツリーを作らない運用でも、`setup` から検索・書き込みまで使える。ワークツリーの作業場所やリポジトリの外部の作業場所・dev-docs の画面からも、登録したフォルダの文書を参照する
- `ref` の引数と `list_changes` の区間は指定できない。`list_changes` は前回参照した時点からの変更だけを返す
- 設定・スキーマ・スクリプトを変えたら `reload` で反映する

> [!WARNING]
> `git clean -x` は Git が無視するファイルも削除します。
> `files.local.yaml` に記載した名前・概要文・タグは、削除されると戻せません。

## スキルで登録する

`/project-index:setup [path]` は、フォルダを配信元として端末の設定に登録します。
`path` を省くと、今の作業場所を対象にします。
`/project-index:global-setup` を済ませ、project-index が待ち受けている必要があります（[project-indexを入れる](./project-indexを入れる.md)）。

<!-- steps -->

1. 端末の設定に `config` がそのフォルダにある行が無ければ（初回）、運用（コミットする・ローカル運用。既定はコミットする）を聞かれる。
   ローカル運用を選ぶと、以降のファイルを `*.local.*` の名前で作り、`info/exclude` に `*.local.*` の行を追加し、端末の設定の行に `storage.type: disk` を記載する。
   2 回目以降は、端末の設定の行の `storage.type` で運用を判定する。
2. 配信元に `project-index.yaml`（ローカル運用は `project-index.local.yaml`）があれば、`check_project` で設定のバージョンの新旧・違反・索引の同期の件数を確かめる。
   違反があれば、キーのパスと理由を示して止まる。端末の設定は書き換えない。
3. `scope.write`・`scope.read` を、既定の値つきで聞かれる。
   既定は、`scope.write` が配信元のパス、`scope.read` が `{path}/**`。
4. `project-index.yaml` が無い配信元（YAML でない範囲）では、範囲の glob（既定 `**/*`）と仮のメタデータ、実装のパスを持つ設計書の種類とキーも聞かれる。
   種類とキーの既定は、YAML の文書の値のうち範囲のファイルのパスに一致する値を持つ種類とキー（無ければ無し）。
   コミットする運用の Git の配信元では、Git が無視するファイルは配信できないため、聞かずに除外する。
   ローカル運用と Git 管理外の配信元では、Git が無視するファイルを除外するかを聞かれる。既定は除外しないで、`.env`・`.env.*` の名前のファイルだけ除外する。
5. YAML でない範囲では、`project-index files` で範囲のうち載せるファイルを求める。
   範囲から `.git`・`node_modules`・`.claude/worktrees` の下のファイルと、除外の条件に当たるファイルは除く。
6. 記載する内容を表で確かめ、了承する。
   断ると、何も書き換えない。
7. YAML でない範囲では、雛形から `project-index.yaml` を作り、`templates/files.schema.yaml` に沿って管理用の YAML に 1 ファイル 1 行を記載する。
8. `check_project` で違反が無いことを確かめ（ローカル運用は `storage_type: disk` と `project-index.local.yaml` の絶対パスを渡す）、端末の設定の `sources[]` に行を記載する。
9. `reload` で配信を始める。
   `/mcp` のセッションは切れず、セッションを張り直さずに `describe` と `search_docs` で使える。
10. alias-inject の端末の設定があり、配信元の設定のファイル（ローカル運用は `project-index.local.yaml`）に `alias_type` を持つ行があれば、alias-inject が読む設定のファイルの一覧（`global.repositories[]`）と突き合わせる。
    同じ Git のリポジトリ（Git 管理外の配信元は同じフォルダ）を指す行の設定のファイルの名前が違えば修正の候補、行が無ければ追加の候補を示す。
    了承すると、`settings.yaml.bak-{日時}` にバックアップを取ってから書き換える。alias-inject の端末の設定が無ければ、何もしない。

<!-- /steps -->

2 回目以降は、`scope`・範囲は聞かず、範囲のファイルと管理用の YAML の行を突き合わせます。
追加・削除・改名の行を表で確かめ、了承されたら `write_docs` で管理用の YAML の行を修正し、`check_project` と `reload` で確かめます。
改名は、Git のリポジトリの配信元（ローカル運用を含む）では Git のリネームの検出、Git 管理外の配信元では内容のハッシュで見つけます。
改名した行は、パスだけが新しくなり、メタデータは元の値を保ちます。

仮のメタデータは、目次のページで分類とタグの語彙を決めてから、`project-index outline` のアウトラインで付けます。
アウトラインで決めにくいファイル（見出しが少ない・コードやログが大半・日本語以外）だけ、見出しの直下の段落・コードブロックの外の文章・全文の順に読みます。
確認の表には、決めた段階と、既存のタグに無い新しいタグを出します。
仮のメタデータを付けた後に、ほぼ同じ `description` の組・1 件だけのタグ・半数以上に付くタグ（`project-index skew`）を、見直しの案つきで同じ表に出します。
確認の時点の記録を持つ配信元では、追加・見直した行を含む組だけを比べ、前回までに断った組を再び出しません。

2 回目以降は、前回の確認の後に中身が変わったファイル（`project-index changed`）のメタデータも見直します。
今の値と新しい案を表で並べ、了承された行だけを書き換えます。
変わっていないファイルは読みません。
記載し終えると、確認の時点を管理用の YAML の `checkpoint` に記録します（`project-index checkpoint`）。

管理用の YAML に行を追加するときと、2 回目以降に関連を持たない行があるときは、確認の表に関連の候補を出します。
テストのファイルには、ファイル名から `test_` の接頭辞（`_test`・`.test` の接尾辞）を除いた名前のコードを指す `tests` を付けます。
同じ名前のコードが範囲に無ければ、候補を付けません。
実装のパスを持つ設計書の種類とキー（初回は手順 4、2 回目以降は表の前に聞かれる）に答えると、その種類の文書を `search_docs` で引いて、そのキーの値とパスが一致するコードに、その設計書を指す `implements` を付けます。
設計書・文書の本文のリンクとパスが指すファイル（`project-index links`）からも候補を出します。

| 指す側 | 指される側 | 候補を付ける行と `type` |
| --- | --- | --- |
| 実装のパスを持つ種類の設計書 | 管理用の YAML の行のコード | 指される側の行に、設計書を指す `implements` |
| それ以外の種類の設計書 | 管理用の YAML の行 | 指される側の行に、設計書を指す `see_also` |
| 管理用の YAML の行の文書 | 配信元の文書 | 指す側の行に `see_also` |

設計書 → コードの向きの関連は記載しません（`trace_related` の `direction: in` でたどります）。
除外の条件に当たるファイルは、行を作りません（[文書のメタデータ](./コアコンセプト-文書のメタデータ.md) の「載せるファイルの判定」）。

範囲のファイルを作った・削除した・改名したときは、そのたびに管理用の YAML の行を修正します。

配信元の直下か、配信元の中のプラグインのルート（`.claude-plugin/plugin.json` を持つフォルダ）に `content/prompts/` があると、そのフォルダを配信する `documents[]` の行を候補に出します。
候補は、初回も 2 回目以降も、管理用の YAML の行と同じ表で確かめます。
同じ `paths` の行が既にあるフォルダは、候補に出しません。
了承すると、project-index の `schemas/prompt.schema.yaml` と、その `$ref` が指す `schemas/common.schema.yaml` を配信元の `schemas/` にコピーし、行と `converters[]`・`nav` の行を `project-index.yaml` に記載します。
記載する行は「プロンプトを配信する」にあります。

## ソースコードを配信する

ソースコードなど YAML でない文書は、管理用の YAML に記載して配信します。

<!-- steps -->

1. 配信するファイルのフォルダに、管理用の YAML `files.yaml` を置く。
   `files[]` に、配信するファイルを 1 ファイル 1 行で記載する。
   共通のタグも各行の `tags` に記載する。
   ```yaml
   files:
     - path: a.py
       tags: [code, auth]
     - path: b.py
       name: 部品 B
       tags: [code]
   ```
2. project-index の `templates/files.schema.yaml` を配信元のフォルダにコピーする。
3. `project-index.yaml` の `documents[]` に、管理用の YAML を指す行を記載する。
   ```yaml
   documents:
     - id: src
       paths: [src/files.yaml]
       schema: schemas/files.schema.yaml
       records: files
       body_file: path
   ```
4. サーバーを起動し、`search_docs` で `tags` が `auth` の文書を引く。
   `a.py` が文書 `src/a.py` として、`name` が `a`・`tags` が `code` と `auth` で返る。

<!-- /steps -->

`files.yaml` に記載していないファイル（除外の条件に当たるファイルを除く）と、ファイルが無い行は、起動時の警告のログに件数が残ります。
キーの一覧は [設定](./設定.md) の「管理用の YAML」、仕組みは [文書のメタデータ](./コアコンセプト-文書のメタデータ.md) にあります。

## 上のフォルダの文書を配信する

設定ファイルをリポジトリの中のフォルダ（例 `content/node-docs/brain/`）に置いたまま、その上のフォルダにある文書を選んで配信できます。

<!-- steps -->

1. 設定ファイルに `paths_base` を記載し、基準にするフォルダを設定ファイルのフォルダからの相対パスで指す。
   `documents[].paths` は基準のフォルダからの相対パスで記載し、`schema` は設定ファイルのフォルダからの相対パスのまま記載する。
   ```yaml
   name: brain
   paths_base: ../../..
   documents:
     - id: knowhow
       paths: [docs/knowhow/*.yaml, content/node-docs/shared/*.yaml]
       schema: knowhow.schema.yaml
   ```
2. `check_project` に設定ファイルのパスを渡して確かめる。
   `paths_base` が設定ファイルのフォルダより下や横・リポジトリの直下より上を指すときと、`paths` が基準のフォルダの外を指すときは、違反で返る。
3. 端末の設定の `sources` に設定ファイルを指す行が無ければ、[手順](#手順) のとおり追加する。
4. `reload` で再読み込みし、`search_docs(source: brain)` で文書を引く。
   文書のパスは基準のフォルダからの相対パス（`docs/knowhow/a.yaml`）で返る。

<!-- /steps -->

`scope.write` の既定と作業中の配信元の判定は、設定ファイルのフォルダのままです。

## プロンプトを配信する

`content/prompts/` に置いたプロンプトの YAML（キーは project-index の `schemas/prompt.schema.yaml`）は、`project-index prompt-doc` の変換で、変数の表・テンプレート・例のセクションを持つ文書として配信します。

<!-- steps -->

1. project-index の `schemas/prompt.schema.yaml` と、その `$ref` が指す `schemas/common.schema.yaml` を配信元の `schemas/` にコピーする。
   ローカル運用では `prompt.schema.local.yaml`・`common.schema.local.yaml` の名前でコピーし、`prompt.schema.local.yaml` の `$ref` の `common.schema.yaml` を `common.schema.local.yaml` に書き換える。
2. `project-index.yaml` に、プロンプトの行と、`project-index prompt-doc` を呼ぶ `converters[]` の行を記載する。
   サイドバーを `kind` ごとにまとめるときは、`nav` に `group_by: kind` の `auto` を記載する。
   フォルダごとにグループ化するときは `group_by: '@folder'` を記載する（`nav` が無いときの既定）。
   ```yaml
   documents:
     - id: prompts
       paths: [content/prompts/**/*.yaml]
       title: プロンプト
       schema: schemas/prompt.schema.yaml
       converter: prompt-doc
       metadata:
         name: name
         description: description
         tags: tags
   converters:
     - id: prompt-doc
       run: [project-index, prompt-doc]
   nav:
     tabs:
       - title: プロンプト
         items:
           - auto: {document: prompts, group_by: kind}
   ```
3. `check_project` と `reload` で配信に入れ、dev-docs の画面でプロンプトのタブを開く。

<!-- /steps -->

プラグインのルートの `content/prompts/` は、`paths` をそのフォルダにした行を別に記載します（`id` は行ごとに変えます）。
`converters[].run` の `project-index` は、PATH に無くても project-index を動かしている Python の環境から引きます。
出力のセクションと終了コードは [CLI](./CLI.md) の「project-index prompt-doc」にあります。

## 起動時の検証

サーバーは起動時に、各配信元の設定（マージした結果）をスキーマで検証し、検査・変換・生成のスクリプトを実行できるかを確かめます。
検証に失敗した配信元は配信せず、配信元の ID・違反したキーのパス・理由をエラーログに記録します。
ほかの配信元は配信します。

| 事象 | 動き |
| --- | --- |
| 配信元の設定がスキーマに違反する | その配信元だけを配信しない。ログは `log_dir`（既定 `${XDG_STATE_HOME:-~/.local/state}/project-index/logs`）に記録する。設定の `version` が古いときは、`project-index migrate --source` で移し替えられることも記録する |
| 端末の設定が無い・スキーマに違反する | 標準エラーに `{ファイル}: {キーのパス}: {理由}` を出し、終了コード 2 で終わる |
| 端末の設定の最上位に、project-index が知らないキーがある | 違反にせず、警告のログに端末の設定のファイルとキーのパスを記録し、配信は始める。キーの値は使用しない。引数なしの `describe` の警告にも載る |
| ポートが使用中 | 標準エラーにポートの番号と `PROJECT_INDEX_PORT` で変えられることを出し、終了コード 3 で終わる |
| プロンプトの YAML が無い・読めない・スキーマに違反する・描画できない | 標準エラーに `{ファイル}: {キーのパス}: {理由}` を出し、終了コード 4 で終わる |
| 設定の `version` がサーバーの参照できるバージョンより古い | 警告のログに配信元の ID・設定のバージョン・サーバーが参照できるバージョンを記録する |
| `alias_type` を持つ行の文書のエイリアスのキーが、alias-inject のスキーマに違反する | 警告のログに文書のパスと違反の内容を記録し、配信は始める。違反した文書は `search_docs` の `term`・`list_match_words` と本文のツールチップに載らない |
| `nav` の `auto` の条件がどの文書にも当たらない | 警告のログにタブと条件を記録し、配信は始める |

配信しなかった配信元を文書の MCP で指すと、違反したキーのパスと理由を返します。

## 設定を変えたら確かめる

配信元の `project-index.yaml`・スキーマ・検査と変換のスクリプトを変えたら、管理の MCP で確かめてから `reload` で配信に入れます。
サーバーの再起動は要らず、`/mcp` のセッションも切れません。

<!-- steps -->

1. `check_project` に配信元のパスを渡し、違反・無いパス・動かないスクリプト・設定のバージョンの新旧・索引の同期の件数を確かめる。
   エイリアスのキーの違反は文書のパスつきの違反で、どの文書にも当たらない `nav` の条件は警告で返る。
   ファイルに記載する前の設定は、`config` に中身を渡して確かめられる。
2. `try_convert` に配信元のパスと文書のファイルを渡し、配信するときと同じ変換の Markdown を確かめる。
   配信元のフォルダは変わらない。
3. `reload` で、変えた設定の配信元を配信に入れる。
   検証に失敗した配信元は外れ、`not_served` に理由が返る。
4. `describe` や `search_docs` で、変えた設定が出ることを確かめる。

<!-- /steps -->

Git 管理外の配信元と `storage.type: disk` の配信元は、`reload` を呼ぶまで変える前の設定で配信し続けます。
Git の配信元は、`default_ref` へ commit した後の要求から変えた設定で配信します（[Git のリポジトリを配信する](#git-のリポジトリを配信する)）。
スクリプトが 0 以外で終わると、`try_convert` が終了コードと標準エラーを返します。
引数と返す内容は [管理のMCP](./管理のMCP.md) にあります。

## 読み取り API

配信中の配信元の文書は、文書の MCP のほかに読み取り API（`/sources` の下）と端末の設定の API（`/settings/sources`）で読めます。
dev-docs の画面のサーバーはこの API から文書を取得して画面に表示します。
入出力は [読み取りAPI](./読み取りAPI.md) にあります。

## 文書の MCP で読み書きする

文書の MCP は `/mcp` の 1 つで、配信元は引数 `source` で指します。
`source` を省くと、作業中の配信元を指します。

<!-- table: {"kind": "data"} -->

| やりたいこと | ツール |
| --- | --- |
| 使える配信元と種類を知る | `describe` |
| 検索・取得する | `search_docs` |
| 作成・更新する | `write_docs` |
| 削除する | `delete_docs` |
| 変更を確かめる | `list_changes` |
| 関連をたどる | `trace_related` |
| 用語の照合に使う語を引く | `list_match_words` |

<!-- /table -->

引数・既定値・上限・エラーは [文書の MCP](./文書のMCP.md) にあります。
どの作業場所からどの配信元を読み書きできるかは [配信元と権限](./コアコンセプト-配信元と権限.md) にあります。
